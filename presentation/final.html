Security

해커가 컨트랙트를 직접 호출하면?

06 / 10

행정 함수

onlyOwner
createVoucherProgram(...)
mintVoucher(...)
approveMerchant(...)
단일 모디파이어 onlyOwner — msg.sender == owner 만 통과한다.
  1. 컨트랙트 owner 키를 모르면 호출 자체 불가능
  2. owner 키는 백엔드 지갑이 단독 보관한다
  3. 모든 행정 액션은 단일 owner 책임으로 귀속된다

결제 함수

4중 검증
useVoucherByMerchant(tokenId, amount, sig, ...)
4중 검증 — 네 단계 중 어느 하나라도 실패하면 트랜잭션 revert.
  1. msg.sender가 가맹점 화이트리스트에 있는가
  2. EIP-712 서명이 토큰 owner 서명과 일치하는가
  3. nonce가 사용 전 상태인가 (재사용 방지)
  4. deadline이 만료되지 않았는가
전제 조건 owner 키는 백엔드 지갑이 단독 보관 — 외부 우회는 차단되며, 내부 키 보안이 시스템 신뢰의 기반이 된다.

왜 ERC-721에 자체 잔액 확장인가

A1 / A3
Q1. ERC-721 위에 잔액 차감 기능을 직접 추가했는데, 왜 표준에서 벗어난 확장을 선택했나요?
ERC-20
잔액 ✓ 식별 ✗

마트 적립 포인트처럼 같은 단위 토큰. 누가 어떤 프로그램의 바우처를 받았는지 추적이 어렵다.

ERC-721 기본
식별 ✓ 잔액 ✗

인증서처럼 토큰별 고유. 그러나 잔액 차감 표준 함수가 없어 부분 결제 불가능하다.

우리 선택
식별 + 잔액 모두

ERC-721 + voucherValue[tokenId] 매핑 자체 추가. VoucherUsed 이벤트로 변경 발행.

정직한 한계 표준 밖이라 외부 익스플로러 자동 인식 불가 → 자체 Verification Layer로 보완한다.

백엔드 우회로 자격 검증을 회피할 수 있나

A2 / A3
Q2. 자격 검증을 백엔드에서만 수행한다면 해커가 컨트랙트를 직접 호출해 우회할 수 있지 않나요?
현재 방어
onlyOwner 모디파이어

외부 우회 시도는 행정 함수의 onlyOwner에서 차단된다. msg.sender == owner이 아니면 트랜잭션 revert.

createVoucherProgram · mintVoucher · approveMerchant
컨트랙트 레벨 검증
EIP-712 + ecrecover 패턴

결제 함수 useVoucherByMerchant에서는 사용자 EIP-712 서명을 ecrecover로 직접 검증한다. 행정 함수 호출자는 onlyOwner로 백엔드 지갑만 허용한다.

전제 조건 외부 우회는 onlyOwner + 4중 검증으로 차단된다. 내부 owner 키 보안은 백엔드 운영 영역에 의존한다.

사용자 QR이 캡쳐되면 도용 가능한가

A3 / A3
Q3. 사용자 QR에는 어떤 정보가 담기며, 캡쳐·도용 시 결제가 일어날 수 있나요?
QR JSON 페이로드
{ "voucherId": 2, "ownerWallet": "0xFFcf…09f0", "ownerNickname": "김청년", "onChainTokenId": 2, "currentValue": 50000, "programName": "청년 식비 지원 바우처", "category": "일반 음식점", "expiryDate": "2026-12-31T23:59", "isValid": true }

식별·메타 정보 9개 노출. 결제에 직접 사용되는 비밀 정보는 포함되지 않는다.

4중 결제 방어
서명 없이는 결제 불가
  1. 가맹점 화이트리스트 — msg.sender가 승인 가맹점인지
  2. EIP-712 사용자 서명 — 바우처 owner 서명이 있어야 함
  3. nonce — 동일 서명 재사용 시 즉시 거부
  4. deadline — 서명 만료 시 무효
→ QR은 "보여주기용 명함" 수준. 도용해도 트랜잭션 발생 불가.
