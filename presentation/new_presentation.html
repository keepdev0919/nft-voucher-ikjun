01 Voucher.sol: onlyOwner

1. 바우처 프로그램 등록 및 발행 통제

어드민(발행 기관)이 예산 한도, 유효 기간, 사용 카테고리를 설정하면 블록체인 컨트랙트 내에 변수로 직접 등록됩니다. 백엔드가 신청자의 나이와 지역을 사전에 검증하고, 검증을 통과한 수혜자에 한해 백엔드 지갑의 관리자 권한(onlyOwner)을 사용하여 온체인 상에 안전하게 NFT 바우처를 발행(mintVoucher)합니다.

02 Voucher.sol: ERC-721

2. 대체 불가능한 소유권 증명

발행된 바우처는 수혜자의 지갑 주소에 1:1로 묶이는 고유한 NFT(ERC-721)로 귀속됩니다. 블록체인 표준 기술을 활용해 타인에게 무단으로 양도되거나 복제되는 것을 원천 차단하고, 지갑 주소를 통해 실제 소유주와 만료일을 실시간으로 확실하게 추적하고 입증합니다.

03 EIP-712 Standard

1. EIP-712 기술

사용자가 서명할 때 결제 조건(금액, 가맹점, 토큰 ID 등)을 메타마스크 화면에 사람이 읽을 수 있는 텍스트로 보여주어 안심하고 결제 서명을 할 수 있도록 돕습니다.

04 ECDSA Verification

2. ECDSA 서명 검증

백엔드 서버가 사용자의 서명을 넘겨받아 가스비를 대신 지불하고 블록체인에 전송합니다. 스마트 컨트랙트는 ECDSA.recover 함수를 통해 서명값으로부터 서명자의 지갑 주소를 역으로 복원한 뒤, 이 주소가 실제 바우처 소유자의 지갑 주소와 일치하는지 판별하여 안전하게 승인합니다.

05 Voucher.sol: _useVoucher

1. 하이브리드 NFT 잔액 실시간 차감

단순히 소유권만 이전하는 일반 NFT(ERC-721) 표준의 한계를 극복하기 위해, 스마트 컨트랙트 내부에 개별 바우처의 잔액 상태값(voucherValue)을 직접 관리하도록 확장 구현했습니다. 사용자가 결제할 때마다 온체인 잔액이 실시간으로 차감되며, 잔액이 0원이 되면 자동으로 사용 완료(USED) 상태로 전환되어 재사용이 원천 차단됩니다.

06 VoucherUsed Event

2. 영수증 해시 온체인 기록

상세한 결제 명세서(구매 물품, 가맹점 정보 등)를 온체인에 그대로 기록하면 막대한 가스비가 발생합니다. 따라서 상세 이력은 백엔드 RDB에 안전하게 저장하되, 해당 영수증 데이터의 해시값을 온체인에 영구 박제합니다. 이를 통해 사후에 백엔드 RDB가 조작되더라도 온체인 해시와 대조하여 데이터 위변조를 즉각 적발해 낼 수 있습니다.

APPENDIX - Q&A

10 / 10

Q1. 왜 ERC-20이 아닌 ERC-721(NFT)을 활용해 설계했나요?

A. ERC-20은 단일 가치만 다루므로 복수의 바우처 관리나 개별 만료일 추적이 어렵습니다. ERC-721을 기반으로 해야 고유 토큰 ID를 활용해 만료 기간, 수혜자 정보, 카테고리 등을 개별적으로 확실하게 통제할 수 있습니다.

Q2. 사용자가 가스비를 안 내면, 백엔드 지갑은 어떻게 가스비를 지출하나요?

A. 대납용 백엔드 지갑의 개인키가 백엔드 환경 설정에 안전하게 보관되어 있으며, 사용자의 MetaMask EIP-712 서명을 받아 백엔드가 대납하여 온체인 트랜잭션 전송을 실행하는 구조입니다.

Q3. 결제 이력을 DB에 저장하면서 온체인 앵커링을 병행한 이유는 무엇인가요?

A. 빠른 실시간 결제와 다량의 이력 관리를 온체인으로만 처리하면 가스비 비용이 너무 큽니다. 따라서 효율적이고 빠른 조회를 위해 상세 이력은 RDB에 저장하되, 무결성 검증용 해시만을 온체인에 기록해 조작을 차단하는 하이브리드 설계를 채택했습니다.

Q4. 사용자가 백엔드 검증을 우회하여 직접 컨트랙트에서 바우처를 발급받으면 어떻게 하나요?

A. 프로그램 생성, 바우처 발급 등 핵심 관리자 함수는 onlyOwner 제어자로 보호됩니다. Owner 권한은 백엔드 서버의 대납용 지갑에만 부여되어 있어, 비인가 계정이 직접 컨트랙트를 호출하더라도 EVM 수준에서 즉시 Revert(실패) 처리됩니다.
